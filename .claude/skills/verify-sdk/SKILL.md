# fa-mcp-sdk end-to-end verification

This skill answers one question: does a project generated by the **published** `fa-mcp-sdk` package build and
run cleanly on a fresh machine? Everything is driven by `scripts/run-verification.js`, which executes the steps
below in order, writes a log per step and prints a pass/fail table.

| Step             | What it does                                                                              |
|------------------|-------------------------------------------------------------------------------------------|
| `global-install` | `npm install -g fa-mcp-sdk@latest`, then compares the installed version with this repo's   |
| `clean-project`  | deletes the previous test project directory                                                |
| `generate`       | `fa-mcp <skill>/config.local.yaml` — must finish without asking a single question          |
| `npm-install`    | `npm install` inside the generated project                                                 |
| `yarn-ci`        | removes `node_modules`, then `yarn ci`                                                     |
| `lint`           | `yarn lint` — oxlint must report nothing                                                   |
| `format`         | `yarn format` — oxfmt `--check` must report nothing                                        |
| `build`          | `yarn cb` — a clean build with no errors                                                   |
| `start`          | `yarn start` in the background, then polls `/health` until it answers `status: healthy`     |

## Before the first run

The scenario is parameterised by **`config.local.yaml` in this skill's directory**. It is the same flat
`key: value` file the `fa-mcp` CLI consumes. The `.local.` in the name puts it outside version control (the
repository `.gitignore` carries a `*.local.*` rule), so machine-specific paths and tokens never get committed.

If the file is missing, copy `config.example.yaml` next to it and set at least `projectAbsPath` (where the
throw-away project is created — **the runner deletes this directory on every run**, so point it at a scratch
location) and `port` (the port the started server listens on).

**Write `projectAbsPath` with forward slashes** — `"D:/DEV/SAND/mcp-test"`. In a double-quoted YAML scalar a
backslash starts an escape sequence, so `"D:\DEV\SAND\mcp-test"` makes the file unparseable; the CLI then falls
back to interactive questions instead of running unattended. The runner rejects such a path up front.

## Running it

```bash
node .claude/skills/verify-sdk/scripts/run-verification.js               # the whole scenario
node .claude/skills/verify-sdk/scripts/run-verification.js --from build  # resume from a step
node .claude/skills/verify-sdk/scripts/run-verification.js --only lint,format
node .claude/skills/verify-sdk/scripts/run-verification.js --keep-running  # leave the server up
node .claude/skills/verify-sdk/scripts/run-verification.js --list        # just list the steps
```

The runner stops at the first failed step and exits with code 1. Per-step logs land in a `verify-sdk-logs`
directory next to the test project (for `projectAbsPath: "D:/DEV/SAND/mcp-test"` that is
`D:/DEV/SAND/verify-sdk-logs`) — deliberately outside this repository, where `_tmp/` is both git-ignored and
hidden from the agent. The console prints only the last 25 lines of a failing step, so open the log file when
that tail is not enough.

The server is started as a tracked child process and stopped by its own process tree. Do not replace that with
`scripts/kill-port.js`: that helper resolves the owner of the port through `netstat`, which also lists the
*client* side of the health-probe connection, so it kills the verification runner along with the server.

A run takes several minutes, most of it in the two dependency installs. Do not shorten the Bash timeout below
20 minutes, and never interrupt an install — a half-written `node_modules` produces failures that have nothing
to do with the SDK.

## The repair loop

A failure is a finding about the SDK, not about the generated project. **Fix the cause in the SDK sources of
this repository, never in the generated copy** — the generated project is deleted on the next run, so a fix
applied there is lost and, worse, hides the defect.

1. **Locate the origin.** The generated project is assembled from `src/template/**` (source code),
   `cli-template/**` (everything else) and `bin/fa-mcp.js` (the generator itself, including the parameter
   substitution and the rewrite of `../../core/index.js` imports into `fa-mcp-sdk`). Runtime failures usually
   come from `src/core/**` or from `package.json` dependency declarations.
2. **Fix it, then prove the SDK itself is clean:** `npm run lint`, `npm run format`, `npm run typecheck`,
   `npm run build`. All four must pass before anything is committed.
3. **Commit.** The `pre-commit` hook bumps the package version automatically — do not bump it by hand.
4. **Push:** `git push`. If the current branch is not `master`, merge it into `master` first and push that.
5. **Publish:** `npm publish`. This is mandatory, not optional — the scenario installs the CLI **from the npm
   registry**, so an unpublished fix changes nothing about the next run. `prepublishOnly` rebuilds the package.
   Publishing is public and irreversible (a version number can never be reused), so **ask the user for
   confirmation before the first publish of a session**; once they have approved the loop, later publishes in
   the same session proceed without asking again.
6. **Re-run the whole scenario from the start.** Not from the failed step — a republished package changes every
   earlier step too. Repeat until the table is green end to end.

If the `global-install` step warns that the registry version is behind the working copy, the run is testing an
older SDK than the code in front of you. Publish first, then re-run; otherwise the result means nothing.

## Failures seen before, and where they came from

- **`ERR_MODULE_NOT_FOUND` on start** — the barrel `src/core/index.ts` re-exports something whose import is
  only in `devDependencies`. Everything reachable from the barrel must be a real `dependencies` entry.
- **`oxfmt --check` fails on a template file** — a multi-line `import` in `src/template/**` collapses under 120
  columns once the generator shortens `../../core/index.js` to `fa-mcp-sdk`. Rewrite the import in the template
  so that both the SDK form and the generated form fit on one line (splitting off an `import type` line works).
- **The generator starts asking questions** — `config.local.yaml` failed to parse; the CLI prints
  `Warning: Could not load config file` and falls back to prompts. Almost always a Windows path with
  backslashes inside double quotes.

## Reporting

Report in the user's language, in full sentences. State for every step whether it passed, and for each failure:
what broke, the cause in the SDK, the fix, the published version that carries it and the result of the re-run.
Never call the scenario green while any step is red or skipped.
