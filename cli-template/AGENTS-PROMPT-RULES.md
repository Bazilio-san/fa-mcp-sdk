# Правила инструкций модели

Читать перед созданием и изменением инструкций, входных данных модели, схем ответа и описаний полей.
Хранить отдельные задания в `llm-tasks/<task>/` соответствующего функционального блока: инструкцию в `prompt.md`,
входной образец в `input.md`, схему в `schema.ts`, сборку в `task.ts`. В библиотеке общие задания проверочного чата
размещать под `src/core/agent-tester/`; в созданном проекте — в каталоге соответствующей службы.

## Краткость и размещение правил

Использовать минимум слов, сохраняющий требования. Каждое правило хранить в одном месте: в инструкции либо описании
поля схемы. Значение и ограничения конкретного поля описывать в его `description`, общие ограничения — в инструкции.
При объяснении длиннее 1024 символов перенести правило в инструкцию, оставив краткую ссылку в поле.
При сокращении сначала удалять повторы, очевидные примеры и ненужные отрицательные примеры, затем оговорки.
Проверять влияние размещения повторными запусками. В описаниях JSON использовать многострочные строки с обратными
кавычками, по одному правилу на строку. Не добавлять отступы перед текстом; значимые пробелы сохранять.

## Входные данные

Простые тексты, даты и виды объектов передавать краткими разделами Markdown с понятными названиями.
JSON применять для вложенных структур, множества однотипных записей, таблиц измерений и связей между объектами.
Не заставлять модель расшифровывать словарь ключей для нескольких простых текстов.
Передавать только сведения, влияющие на ответ. Не включать историю происхождения данных, устройство хранения,
получателей результата и последующие процессы, если это не меняет критерий решения.
Не добавлять имя и должность человека, когда достаточно вида объекта. Критерий оценки описывать прямо и кратко.

## Проверка

Сверять утверждения инструкции о входе с фактическим сборщиком данных. Вместо неверного утверждения об отсутствии
дат объяснять, как обрабатывать даты внутри текста. Новую формулировку проверять повторными запусками на примерах:
перефразирование, повторы, добавление неизменности, изменение отрицания, степени, уверенности и дат.
Принимать только устойчивый приемлемый результат. Проверять фактически отправленный запрос, схему и ответ через
управляемую диагностику. Не раскрывать ключи доступа.
