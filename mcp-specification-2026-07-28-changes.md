# Последние изменения в спецификации MCP

**Актуальная стабильная версия:** `2026-07-28`  
**Дата выпуска:** 28 июля 2026 года  
**Предыдущая версия:** `2025-11-25`

Версия `2026-07-28` — крупное обновление Model Context Protocol с существенными изменениями транспорта, жизненного цикла запросов, расширений, авторизации и кэширования.

---

## 1. MCP стал stateless

Из ядра протокола убраны:

- `initialize`;
- `notifications/initialized`;
- `Mcp-Session-Id`;
- обязательное поддержание протокольной сессии между клиентом и сервером.

Теперь запрос должен содержать необходимые сведения о версии протокола и возможностях клиента в `_meta`.

Для отдельного предварительного получения возможностей сервера введён метод:

```text
server/discover
```

Практический смысл:

- запросы не требуется направлять на тот же экземпляр сервера;
- отпадает необходимость в sticky sessions;
- MCP-серверы проще масштабировать через обычные HTTP-балансировщики;
- прикладное состояние должно передаваться явно, например через `browser_id`, `task_id`, `basket_id` или другой handle.

---

## 2. Multi Round-Trip Requests — MRTR

Вместо прежней модели server-to-client запросов вводится механизм многошагового выполнения запроса.

К этой области относятся сценарии, ранее реализованные через:

```text
elicitation/create
sampling/createMessage
roots/list
```

Сервер может вернуть промежуточный результат:

```json
{
  "resultType": "input_required",
  "inputRequests": {
    "confirm": {
      "type": "elicitation",
      "message": "Удалить файлы?"
    }
  },
  "requestState": "..."
}
```

После получения пользовательского ответа клиент повторяет исходный запрос и добавляет ответы:

```json
{
  "inputResponses": {
    "confirm": true
  }
}
```

MRTR позволяет:

- запрашивать подтверждение опасной операции;
- уточнять недостающие параметры;
- выполнять промежуточное обращение к модели;
- продолжать операцию без постоянного двунаправленного соединения.

---

## 3. Поле `resultType`

Результаты запросов теперь явно обозначают состояние выполнения.

Завершённый результат:

```json
{
  "resultType": "complete"
}
```

Ожидание дополнительных данных:

```json
{
  "resultType": "input_required"
}
```

Для обратной совместимости старый ответ без `resultType` клиент может трактовать как завершённый.

---

## 4. HTTP-заголовки маршрутизации

Для Streamable HTTP POST определены заголовки, позволяющие инфраструктуре определить MCP-операцию без разбора JSON-тела:

```http
Mcp-Method: tools/call
Mcp-Name: search
```

Это полезно для:

- API Gateway;
- WAF;
- rate limiting;
- логирования;
- балансировки;
- политик доступа для отдельных инструментов.

Также спецификация описывает `x-mcp-header`, позволяющий связывать данные схемы с пользовательскими HTTP-заголовками.

---

## 5. Кэширование tools, prompts и resources

Для списков и чтения ресурсов добавлены рекомендации по кэшированию.

Пример:

```json
{
  "ttlMs": 60000,
  "cacheScope": "private"
}
```

Изменения затрагивают, в частности:

- `tools/list`;
- `prompts/list`;
- `resources/list`;
- `resources/read`;
- `resources/templates/list`.

Где:

- `ttlMs` — рекомендуемый срок актуальности ответа в миллисекундах;
- `cacheScope` — область кэширования, например `public` или `private`.

Инструменты рекомендуется возвращать в детерминированном порядке. Это уменьшает ненужные изменения промпта и помогает эффективнее использовать prompt caching модели.

---

## 6. Новый механизм подписок

Старая модель отдельных подписок и отдельного HTTP GET-потока заменяется единым механизмом прослушивания:

```text
subscriptions/listen
```

Клиент может выбрать интересующие категории событий, например:

- `toolsListChanged`;
- `promptsListChanged`;
- `resourcesListChanged`;
- `resourceSubscriptions`.

Уведомления могут связываться с подпиской через идентификатор:

```text
io.modelcontextprotocol/subscriptionId
```

Прогресс и диагностические события конкретного запроса при этом могут передаваться в потоке ответа этого запроса.

---

## 7. Tasks вынесены в расширение

Долгие и фоновые операции больше не развиваются как часть обязательного core-протокола. Для них используется официальное расширение:

```text
io.modelcontextprotocol/tasks
```

Среди ключевых изменений:

- Tasks оформлены как extension;
- удалён прежний `tasks/list`;
- получение результата строится вокруг проверки состояния через `tasks/get`;
- добавлен `tasks/update` для передачи новых данных в выполняющуюся задачу;
- сервер может вернуть task handle для дальнейшей работы.

Это позволяет использовать Tasks только тем клиентам и серверам, которым действительно нужны долгие операции.

---

## 8. Формальный Extensions Framework

В возможностях клиента и сервера появилось поле:

```json
{
  "extensions": {}
}
```

Расширения позволяют развивать дополнительные возможности MCP отдельно от обязательного ядра.

К официальным направлениям расширений относятся:

- Tasks;
- MCP Apps;
- Enterprise-Managed Authorization.

Преимущество такого подхода: core-протокол остаётся компактнее, а специализированные возможности могут версионироваться независимо.

---

## 9. MCP Apps

MCP Apps позволяет серверу предоставлять клиенту интерактивный интерфейс, связанный с инструментом.

Возможные интерфейсы:

- формы;
- графики;
- таблицы;
- панели мониторинга;
- подтверждения операций;
- специализированные мини-приложения.

Для UI-ресурсов используется URI-схема:

```text
ui://...
```

MCP Apps является расширением, а не обязательной частью основного MCP-протокола. Поддержка зависит от конкретного MCP-host/client.

---

## 10. JSON Schema 2020-12

Схемы входных и выходных данных получили полноценную ориентацию на JSON Schema 2020-12.

Это относится к:

- `inputSchema`;
- `outputSchema`;
- разрешению `$ref`;
- составным схемам `allOf`, `anyOf`, `oneOf`;
- структурированным результатам инструментов.

`structuredContent` может представлять не только объект, но и другое допустимое JSON-значение, если это соответствует объявленной схеме.

---

## 11. Изменения авторизации

Спецификация усиливает требования вокруг OAuth и OpenID Connect.

Основные направления:

- проверка issuer — `iss`;
- изоляция credentials для каждого authorization server;
- запрет небезопасного переиспользования credentials между разными issuer;
- более точные требования к регистрации клиентов;
- переход от Dynamic Client Registration к Client ID Metadata Documents.

Dynamic Client Registration объявляется устаревающим подходом, а Client ID Metadata Documents рассматривается как предпочтительное направление.

---

## 12. OpenTelemetry и трассировка

Для `_meta` стандартизированы поля W3C Trace Context:

```text
traceparent
tracestate
baggage
```

Это позволяет связывать трассировку между:

- MCP-клиентом;
- MCP-host;
- gateway;
- MCP-сервером;
- внешними сервисами и API.

---

## 13. Deprecated-возможности

В версии `2026-07-28` формализована политика устаревания возможностей.

В число deprecated-направлений входят:

- Roots;
- Sampling;
- Logging как отдельная MCP-возможность;
- старый HTTP+SSE transport;
- устаревшие варианты `includeContext`;
- Dynamic Client Registration как основной механизм регистрации.

Рекомендуемые направления замены:

| Устаревающий механизм | Рекомендуемый подход |
|---|---|
| Roots | Явные аргументы tools, resource URI или конфигурация сервера |
| Sampling | Прямое подключение сервера к API модели либо MRTR-сценарий |
| Logging | `stderr`, инфраструктурные логи и OpenTelemetry |
| HTTP+SSE | Streamable HTTP |
| Dynamic Client Registration | Client ID Metadata Documents |

Спецификация вводит формальную deprecation policy, чтобы функции удалялись предсказуемо, а не внезапно.

---

## 14. Что потребуется изменить при миграции

При переходе с MCP `2025-11-25` на `2026-07-28` следует проверить:

1. Нет ли зависимости от `Mcp-Session-Id`.
2. Не предполагает ли сервер обязательный `initialize`.
3. Передаются ли сведения о версии и capabilities в `_meta`.
4. Реализован ли `server/discover`, если требуется предварительное обнаружение возможностей.
5. Возвращается ли корректный `resultType`.
6. Поддерживаются ли `Mcp-Method` и `Mcp-Name` для HTTP-маршрутизации.
7. Переделаны ли elicitation и другие многошаговые операции на MRTR.
8. Возвращаются ли `ttlMs` и `cacheScope` там, где это предусмотрено.
9. Перенесены ли долгие операции на Tasks extension.
10. Поддерживает ли используемый SDK версию спецификации `2026-07-28`.
11. Обновлена ли OAuth-логика с учётом issuer и Client ID Metadata Documents.
12. Удалены ли архитектурные предположения о постоянном двунаправленном соединении.
